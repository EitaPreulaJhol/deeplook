## 1. Approved fixes

### 1.1 BOM at the start of `.env` and tracked files — ✅

`.env` starts with the UTF-8 BOM (`EF BB BF`). `docker compose` accepts it, but bash's
`source .env` reads the first variable with the BOM stuck to its name. Four tracked files have a
BOM: `.env.example` (which `.env` was copied from), `.gitignore`, `docker-compose.yml` and
`scripts/ui-playwright/run.ps1`.

Also, `.gitignore` only ignores `.env` and `.env.local`. A copy such as `.env.bak` or `.env.prod`
would be committed without warning (which nearly happened with the 2026-11-13 backup).

**What to do:**

- Remove the BOM from `.env`, `.env.example`, `.gitignore` and `docker-compose.yml`. `run.ps1`
  stays as it is: PowerShell 5.1 needs the BOM to read UTF-8.
- Replace the `.gitignore` lines with `.env` and `.env.*`, with the `!.env.example` exception.
- To keep it from coming back: an `.editorconfig` with `charset = utf-8` and a CI check that
  fails on a BOM in tracked files (with `run.ps1` as the exception).

**How to validate:** `docker compose config` identical before and after, `set -a; . ./.env`
without errors, and `git check-ignore .env.bak` reporting the file as ignored.

**Done:** BOM removed from the four files (`run.ps1` kept it, and the check allows a BOM in `*.ps1`),
`.env.*` with the `!.env.example` exception in `.gitignore`, `.editorconfig` and
`scripts/check-bom.mjs` in the CI `check` job, plus a note in the deployment checklist. Verified:
`docker compose config` gave the same hash before and after, `. ./.env` now works (before:
`#: command not found`) and the check rejects a file with a BOM.

### 1.2 Automatic check for untranslated API errors — ✅

`apps/api/src/lib/messages-en.ts` (317 pairs) is maintained by hand. A new or changed error
message with no pair in the dictionary goes out in Portuguese to English interface users, and
nothing flags it.

**What to do:** a unit test (`tests/unit/messages-coverage.test.ts`) that:

1. Walks `src/**/*.ts` and extracts the texts of error responses: `.send({ error: '...' })`,
   `details` and the messages of the error classes that reach the client (`ZipError`,
   `RestoreError`, `ImportError`, `ProxmoxError` and the others). It reuses the extractor that
   built the dictionary in item 2.5. `${...}` parts become `{0}`, `{1}`... in the dictionary's
   format.
2. Fails on each text with no pair in `MESSAGES_EN`, naming the file and line.
3. Fails on dictionary pairs that no text in the code uses any more, so dead entries don't pile
   up.

Texts that are not errors but match the pattern go into an exception list in the test itself,
each with its reason. The test runs in `test:unit`, which is already in CI.

**Done:** `apps/api/tests/unit/messages-coverage.test.ts`. The extractor now joins `+`
concatenations and looks at Portuguese that only appears inside a `${...}`; those two gaps left
four dictionary pairs looking unused. Exceptions live in two lists in the test itself: files that
never answer a request (`.env` validation, command-line restore, Proxmox simulator) and texts that
are stored or computed data (background analysis failures, system status, YARA hold reasons, AD
reasons), which belong to 1.4.

The test found 22 messages reaching the client in Portuguese, now translated:

- the file missing from storage (download 404);
- the backup password rule;
- the YARA pack check errors, which the route forwards nested;
- the Proxmox errors, which the sandbox route forwards in a 502.

In the Proxmox message, the permission hint came right after the PVE detail, which usually has a
dot (`VM.Clone`), and the dictionary couldn't find where it started. It now comes after
`Permissões:` ("Permissions:"). A test in `error-language.test.ts` covers that case, and a negative
test (a made-up new message in a route) confirmed the check fails.

### 1.3 A single `buildApp()` for production and the integration tests — ✅

`src/index.ts` builds the Fastify app (cookies, rate limit, multipart, websocket, the language hook
and about 50 routes) and starts the server right away. Each of the 40 files in
`tests/integration` builds its own version with only the routes it uses. That is why the language
hook (2.5) only applied in the `operations` test after being registered there by hand. Any new
global hook (header, error handling, logging) has the same problem.

**What to do:**

- Split out `src/app.ts` with `buildApp(options)`: builds and registers everything but does not
  call `listen` or start the background jobs. `index.ts` calls `buildApp()`, then `listen` and
  the background jobs.
- `options` covers what the tests swap today: the logger, the fake clients (Proxmox, S3, LDAP) and
  which routes to register, if limiting them is still needed.
- Migrate the tests in batches, simplest first, running the integration suite after each batch. A
  test that needs to build the app differently becomes an exception documented in its own file.

**How to validate:** the whole integration suite green (currently 1478 checks in 41 files) and a
new test that checks, through the production app, an English error with `Accept-Language: en`.

**Done:**

- `apps/api/src/app.ts` exports `buildApp(options)` and the `ROUTES` list. `index.ts` keeps only
  what belongs to the process: the background-job logger, startup tasks, signals, `listen` and the
  queues. The options are `logger`, `trustProxy`, `network` and `beforeRoutes`.
- The integration tests now use `buildApp()`. The migration was scripted, with import cleanup
  driven by `tsc`, and each batch was run right after. Four minimal `Fastify()` instances remain,
  each commented in its own file:
  - three in `boundaries`, which test the network policy and the cookie name, not the app;
  - one in `operations`, which needs a 1 KB upload limit.
- The two WebSocket tests use `trustProxy: false`: `injectWS` simulates the connection without a
  socket, and with `trustProxy` Fastify reads the socket address.
- New test, `app.test.ts`, which checks:
  - that every route in `src/routes` is in `ROUTES`;
  - the 404 and 401 in English;
  - the refusal of a cross-site request;
  - invalid JSON and an unexpected error handled by the API's error handler.

**Production bug found along the way:** `index.ts` set the error handler after registering the
routes, and in Fastify each plugin inherits the handler that existed when it was loaded. So the
handler never applied to the routes. In practice:

- an unexpected error went out in Fastify's format, with the **whole internal message** sent to
  the client (a Prisma or S3 failure, for example);
- the handler's 404 for a file missing from storage never happened in the routes;
- the interface showed "Internal Server Error" or "Bad Request" instead of the API message.

`buildApp()` sets the handler before the routes, and `app.test.ts` covers it. An isolated test
confirmed the old behaviour: with the handler set afterwards, the response carried the thrown
error's message.

**Coverage effect:** `own-samples`, which checks access to every sample route, went from 94 to 104
checks. It now sees the capa, Ghidra, unpack, oletools, risk and other routes its list lacked, and
they all passed.

**Validation:** the whole integration suite with 1762 checks in 51 files; unit tests, types,
ESLint, Prettier and the API build; and `test:smoke`, with the real images.

### 1.4 API data stored in Portuguese becomes code + parameters — ✅

The English interface translates the screens and the errors, but whatever the API stores as a
ready-made sentence is still in Portuguese. It shows up in sample pages, history, notifications
and status. Initial inventory:

| Where | Source | How it is kept |
|---|---|---|
| Risk score reasons | `src/lib/risk-score.ts` | `{ source, text, weight }`, computed on request |
| Static analysis alerts | `pe-analysis`, `pe-dotnet`, `elf-analysis`, `lnk-analysis`, `doc-analysis`, `script-analysis`, `disk-image`, `unpack` | list of texts inside `Entry.staticInfo` |
| oletools alerts | `src/lib/oletools.ts` | `OfficeAnalysis.alerts` (`{ level, text }`) |
| Reputation summary | `src/lib/reputation.ts` | `ReputationCheck.summary` |
| YARA hold reasons | `src/lib/yara-update.ts` | `YaraPackRelease.reasons` |
| Sample and case history | sample and case routes | `EntryEvent.fromValue`/`toValue`/`detail`, `CaseEvent` |
| Notifications | `src/lib/notifications.ts` | `Notification.detail` |
| Audit (screen and CSV) | `src/lib/audit.ts` | `AuditEvent.detail` |
| System status | `src/lib/status.ts` | computed on request (77 texts) |
| OpenAPI descriptions | `src/lib/openapi.ts` | computed on request |

The full inventory is the item's first step. There are two cases with different solutions:

- **Computed on request** (risk, status, CSV, OpenAPI): the API answers in the request's
  language, with the existing `requestLang()`. Nothing changes in the database.
- **Stored** (alerts, history, notifications, audit, reputation, holds): stores
  `{ code, params, text }` instead. `code` is stable (e.g. `pe.tlsCallback`), `params` carries the
  values (names, numbers, hashes) and `text` stays in Portuguese. The web builds the sentence from
  `code` with a new dictionary (`apps/web/src/i18n/data.ts`) and falls back to `text` for an
  unknown code. Old records, without `code`, show as they are.

The Portuguese `text` stays for three reasons: scripts and integrations reading the API don't
break, the audit stays readable in the database, and a new code the web doesn't know yet doesn't
vanish from the screen.

**Suggested order** (each part is one commit and usable on its own):

1. Risk and status: computed on request, no migration.
2. Static analysis and oletools alerts: what shows most on the sample page.
3. History, notifications and audit.
4. Reputation, YARA holds, CSV and OpenAPI.

**Out of scope:** translating old records. A re-analysis stores the new format; whatever isn't
re-analysed stays in Portuguese.

**How to validate:** the web's `check-i18n` also counts untranslated codes; the Playwright English
sweep (`i18n.mjs`) gains a sample with alerts, risk and history; and the integration tests check
`code` and `params` of the new alerts.

**Progress:**

- **Part 1 (risk and status): ✅.**
  - The status comes out in the request's language through both routes, `/api/admin/status` and
    `/api/status` (the token one). It is translated by a pattern dictionary in
    `apps/api/src/lib/status-en.ts`, with the same translator as the errors, now `createTranslator`.
  - The risk reasons and the in-progress items are built in the request's language, with lists
    translated ("e mais 2" / "and 2 more").
  - When the language changes, the web fetches the cached queries again.
  - The `tests/unit/status-language.test.ts` test fails on a status text without a translation. The
    extractor shared by both translation tests lives in `tests/unit/source-texts.ts`.
  - List items that come from other analyses (PE and oletools alerts) stay in Portuguese until
    part 2.
- **Part 2 (analysis alerts and reasons): ✅.**
  - **Change of approach:** instead of storing `{ code, params, text }`, the API translates on
    output what the analyses stored, with the same pattern dictionary and translator as the errors
    and the status (`apps/api/src/lib/data-en.ts` and `data-language.ts`). Old records also come
    out in English (as long as the sentence didn't change), the database and the response format

  - It covers the PE, .NET, ELF, shortcut, disk image, document and script alerts, the oletools

  - Routes: the sample page, re-analysis, sample comparison and each analysis's route. In

  - The PE and oletools alerts quoted in the risk reasons also come out translated, which closes

  - The `tests/unit/data-language.test.ts` test fails on an analysis sentence without a
    translation. It scans more widely than the Portuguese detector, which let through sentences
    with no accent or preposition ("nome forte").
  - The unpack child sample's title and description, which people edit, stay as they are.
- **Part 3 (history, notifications and audit): ✅.**
  - Same mechanism, with the dictionary in `apps/api/src/lib/history-en.ts`. A detail built with

  - Only system text goes through the dictionary:
    - in the sample history, the purge, capture, extraction, triage rule, sandbox and automatic

  - The audit CSV comes out in the interface language, with header, action name, detail and

  - The reputation summary and service names, the YARA pack hold reasons and last check failure,

## 2. Features

### 2.1 Sample download inside a password-protected ZIP — ✅

Today `GET /api/entries/:id/download` delivers the raw file as `application/octet-stream`. nginx
and the headers keep the browser from opening it, but the whole file lands on the analyst's disk.
There the antivirus may delete it mid-work, and an accidental double-click runs it. The field's
custom is a ZIP with the password `infected`.

**Format: ZipCrypto, with the fixed password `infected`.** The password is public, so the cipher
is only packaging and ZipCrypto's weakness doesn't matter. What matters is opening in Windows
Explorer without installing anything. The AES-256 the backup's `zip-writer.ts` already uses only
opens in 7-Zip.

**What to do:**

- API: `GET /api/entries/:id/download?format=zip|raw`. The ZIP is streamed, never written to
  disk: a single entry with a data descriptor (the CRC is only known at the end) and ZIP64 above
  4 GB. The file inside the ZIP keeps the sample's original name, and the ZIP is named
  `<original name>.zip`. The integrity check (SHA-256 and size) still runs over the original
  bytes, as today.
- The API default stays `raw`, so token scripts don't break. The interface asks for `zip`.
- Web: "Download sample" downloads the ZIP, with the password written next to the button.
  "Download original file" goes into a menu, with a confirmation explaining the risk.
- The audit log (`ENTRY_DOWNLOADED`) records the format.
- Document the password and the parameter in the README and the OpenAPI.

**How to validate:**

- Writer unit test: the ZIP opens with `unzip` and `7z` for sizes 0, 1 byte, 64 KiB and over 4 GB
  (the last one simulated with a synthetic stream), and a wrong password fails.
- Integration: both formats, the audit record and the integrity warning with the ZIP.
- Playwright: the new button and the confirmation for the original.

**Done:**

- `apps/api/src/lib/sample-zip.ts` streams the ZIP at about 200 MB/s: the largest sample accepted
  today (`MAX_UPLOAD_MB=200`) takes 1 s of CPU. The route accepts `?format=zip|raw`, answers with
  an exact `Content-Length` and the `X-DeepLook-Zip-Password` header, and the audit log records
  `ZIP com senha (infected)` or `arquivo original`.
- On the web, the button became "Download sample (ZIP)", with "password: infected" next to it.
  "Download original file…" is in the More menu, with a confirmation.
- **Plan correction:** API tokens can't download samples (`lib/api-tokens.ts`), so the route
  isn't in the OpenAPI and there are no token scripts to protect. The default stays the raw file
  only for compatibility with old links; the interface always asks for the format.
- **Tests:**
  - `tests/integration/sample-zip.test.ts`: 63 checks. Sizes 0, 1 byte, 64 KiB and 5 MiB, and
    forced ZIP64. Each ZIP opens in the project's reader, `unzip`, `python` and `7z`, with the
    content checked by SHA-256; a wrong password is refused; the 4 GB threshold is computed
    without producing 4 GB.
  - In `sample-access` and `integrity`: the headers, the audit log, an invalid format (400) and
    the integrity warning with the ZIP.
  - In Playwright, `sample-access.mjs` covers the button, the password, the confirmation and who
    sees the item.
- **Not tested here:** opening in Windows Explorer, for lack of a Windows machine. The format is
  the same as Info-ZIP's `zip -e`.

### 2.2 QR codes in attachments, PDFs and captures — ✅

QR code phishing (boleto included) gets past filters because the link isn't in the text. Today the
e-mail's links show on the sample page and go into the suggested IOCs, but a QR code in an image, a
PDF or the captured page shows up nowhere.

**Where to decode:** outside the API, like every parser of hostile content in the project.

- Page screenshot of a link sample: in the `capture` service, which already has the pixels (it
  computes the perceptual hash), with a JavaScript decoder.
- Images (`.eml` attachments and image samples) and PDF pages: in the `oletools` service, which
  already receives documents. It gains `zxing-cpp` and `pypdfium2` to rasterize the first pages.
- Explicit limits: pages per PDF, pixels per image, images per sample and total time.

**On the sample page:**

- A "QR codes" section with each code's content and where it came from (attachment, PDF page,
  screenshot).
- Decoded URLs go into the suggested IOCs, like the e-mail's links.
- An "Analyse this link" button creates a new link sample that cites the original.
- The risk score gains a new reason: a QR code with a URL in an e-mail or document.

**How to validate:** test samples with a QR code in a PNG, in a JPEG inside an `.eml`, in a PDF and
on a page served by the capture simulator; and the refusals above the limits.

**Done:**

- **Reader:** the `oletools` service gained `POST /qr` (`apps/oletools/qr.py`, with zxing-cpp,
  pypdfium2 and Pillow, pinned by hash in the lockfile), on the same skeleton as `/analyze`: token,
  child process with a time limit, one container per job. Limits: 5 PDF pages, 40 million pixels per
  image or page, 20 codes and 2000 characters per code.
- **Change from the plan:** the page screenshot also goes to that reader, instead of a JavaScript
  decoder in the capture service. There is a single reader (zxing-cpp, more robust), and the capture
  gains no new dependency.
- **API:** the `QrScan` table, with its own queue modelled on oletools' (`apps/api/src/lib/qr.ts`).
  It runs on every image (PNG, JPEG, GIF) or PDF upload, including `.eml` attachments, which become
  samples, and at the end of every link capture, with the latest screenshot. The
  `GET/POST /api/entries/:id/qr` route shows the result to whoever sees the sample and lets an
  analyst ask again. The risk score gained the "QR code with a link" reason (weight 15).
- **Web:** the "QR codes" section of the sample page, with each code's content and origin.
  Addresses go into the suggested IOCs, and the "Analyze this link" button creates a link sample
  that cites the original in its description.
- **Tests:** `tests/integration/oletools-qr.test.ts`, against the real service, with a PNG, a PDF
  with the QR drawn as vectors, text that is not an address, an executable (not applicable), a link
  sample screenshot, risk and access. Also the `scripts/ui-playwright/qr.mjs` scenario and
  `own-samples`, which now covers the two new routes.

### 2.3 Triage and YARA rule effectiveness — ✅

Show, for each rule, how often it fired and in how many of those the sample ended with a Clean
verdict. A rule that fires often on clean samples is a candidate for tuning; a rule that never
fires may be broken.

**Where the numbers come from:**

- YARA: each sample's `YaraScan.matches`, joined with `Entry.verdict`.
- Triage: the `TRIAGE_RULE` history events. Today they store the rule's **name** (`toValue`), and
  renaming breaks the count. New events also store the rule id; old ones are counted by name while
  it still matches.

**On screen:** "Fired (90 days)" and "% on clean" columns in the triage and YARA rule lists,
sortable, and a "never fired" filter. The numbers are computed on demand, with no new table. If it
gets slow, a daily summary comes in.

**How to validate:** integration with samples and known verdicts; check the count after renaming a
rule.

**Done:**

- `apps/api/src/lib/rule-effectiveness.ts` computes the numbers on each request, with no new
  table; samples in the trash are left out. The triage, team YARA and pack YARA rule lists now carry
  `effectiveness: { fired, clean }`.
  - YARA: each sample's latest scan done in the last 90 days, by rule set name.
  - Triage: the history events. The event now stores the rule id in `fromValue`, which it didn't
    use, with no migration; older events count by name while the rule keeps that name.
- **Limitation:** the triage event is only stored when the rule changes something on the sample
  (tag or priority). So "fired" means the times the rule changed a sample; if the sample already had
  the tag, it doesn't count.

### 3.4 Assessment: Docker secrets

**Conclusion:** it would change quite a lot for a small gain in this installation (one host,
Compose without Swarm). Not recommended now.

**What would have to change:**

| Part | Change |
|---|---|
| Secrets | 18 values: `SESSION_SECRET`, `DATA_KEY`, `DATA_KEY_PREVIOUS`, `POSTGRES_PASSWORD`, `MINIO_ROOT_PASSWORD`, `S3_SECRET_KEY`, `ADMIN_PASSWORD`, `LDAP_BIND_PASSWORD`, `PROXMOX_PASSWORD`, `BACKUP_SCHEDULE_PASSWORD`, the five service tokens and the three reputation keys |
| `docker-compose.yml` | a `secrets:` block and the secret list in 9 services |
| API | reading `*_FILE` before `env.ts`; `DATABASE_URL` carries the database password and would have to be assembled at run time, in `docker-entrypoint.sh` (for `prisma migrate deploy`) and in `prisma.config.ts`; `seed.ts` and `restore.ts` read `process.env` directly |
| Services | `capture` (Node) and `capa`, `ghidra`, `unpack`, `oletools` (Python) reading `*_FILE`. Postgres and MinIO already accept `*_FILE` |
| Tests | `tests/run.mjs` and `tests/smoke.mjs` set up the environment through variables and would have to generate the files |
| Documentation | the README variable table (about 45 mentions), the deployment checklist and the `DATA_KEY` rotation |
| Existing installation | split `.env` into one file per secret, with the right permission for each container |

**The practical obstacle, tested on 2026-11-13:** without Swarm, Compose (5.7.1) mounts the secret
as a bind of the host file. It keeps the original owner and mode and ignores `uid`, `gid` and
`mode`. A `600` file owned by user 1000 can't be read by Postgres (uid 999), and the project's
services run as seven different users (`node`, `pwuser`, `capa`, `ghidra`, `unpack`, `oletools`,
`postgres`, plus MinIO). That leaves two bad options: world-readable files inside a `700` folder,
or a per-file `chown` to each image's uid, which breaks when an image changes its uid.

**The gain:** the values leave `docker inspect` and `docker compose config`, and are no longer
inherited by child processes. But whoever runs `docker inspect` has access to the Docker socket,
which is already root-equivalent on the host and allows `docker exec cat /run/secrets/...`. In the
analysis services, the tool reading the malicious file runs as the same user that would read the
secret from disk. The real gain is avoiding accidental leaks, such as pasting `docker inspect`
output into a ticket.

**Cheap alternative (S), if accidental leaks are a concern:** accept `NAME_FILE` next to `NAME` in
the API and the services, without changing the default compose. Whoever wants it can use it; the
current installation doesn't change. The `.env` with mode `600` (review item 2.2) stays the main
protection.

### 5.2 Centralized alert log

With `ALERT_LOG_DIR` in `.env` (the host folder), the API writes one JSON line per alert to `deeplook-alerts.jsonl`, for a collector
(Filebeat, Fluent Bit, rsyslog, Wazuh) to ship to the SIEM. Without the variable, nothing is
written. The compose mounts the folder (`ALERT_LOG_DIR`, default `./data/alerts`).

Each line carries `time`, `level` (`warn` or `error`), `code` (stable, for filtering), `message` (in
Portuguese) and `context` (ids, names). The alerts:

- scheduled backup failure;
- a component going to error in the system status (and back to normal);
- broken audit chain;
- a file not matching its SHA-256 (on download or in the periodic check);
- a YARA rule update held for approval.

The same alert doesn't repeat while the state doesn't change (a component that goes down produces
one line when it falls and another when it comes back, not one a minute). The file is opened in
append mode on every line, so external rotation (`logrotate` with `copytruncate` or `create`) works
without restarting the API.

**Done:** `apps/api/src/lib/alert-log.ts` and the five hooks (backup, status through a 5-minute
monitor, audit, integrity, held YARA update). The compose derives the path from `ALERT_LOG_DIR`
(empty turns it off), like `BACKUP_DIR`. Tests: unit (format, off, state change, path without
permission) and integration (tampered file; the capture pointed at a closed port and turned off
again: two lines, no repeats).

### 5.4 Network capture through the MikroTik

Pieces:

1. **`netcap` service** (new, Node, no dependencies): receives the CHR sniffer traffic over TZSP
   (UDP 37008), splits packets by each VM's MAC and writes one pcap per session. An HTTP API with a
   token (`POST /sessions`, `DELETE /sessions/:id`, which returns the pcap) controls it. Size and
   packet limits per session. No root, read-only root, writing to a tmpfs.
2. **Sniffer control:** when an environment opens, the API reads the VM's MAC (`net0` of the clone),
   opens the session in `netcap` and adds the MAC to the CHR sniffer's `filter-mac-address` list
   (`/tool/sniffer`, through the REST API), streaming over TZSP to `netcap`. On close, it removes the
   MAC and, with no active environment left, stops the sniffer. Variables: `MIKROTIK_URL`,
   `MIKROTIK_USER`, `MIKROTIK_PASSWORD`, `MIKROTIK_VERIFY_TLS` and `NETCAP_STREAM_TARGET` (the address
   the CHR reaches).
3. **`suricata` service** (new, the Suricata image with an HTTP server on the same skeleton as the
   others): receives the pcap, runs `suricata -r` and returns a summarized `eve.json`: alerts, DNS,
   HTTP and TLS (SNI and certificate). The ET Open rules are downloaded with `suricata-update` at
   startup and once a day, through the controlled egress (`egress`); the analysis itself runs
   without network.
4. **On the sample page:** the pcap goes to MinIO, like the screenshots, and into the backup and
   the trash. The environment section shows the Suricata alerts, DNS queries, HTTP requests and TLS
   names, plus the pcap download. Domains and IPs go into the suggested IOCs, and a Suricata alert
   adds to the risk score.
5. **Off:** without `MIKROTIK_URL` or `NETCAP_URL`, nothing changes in the sandbox. Without
   Suricata, only the pcap stays.

**Test:** without the CHR, a server that imitates the RouterOS REST API and a TZSP packet generator
cover the whole path in integration. Suricata runs for real, with a test rule. The test against the
real CHR is left out (see 5.5).

**Network:** `netcap` must receive UDP from the CHR. The port is published on the host
(`NETCAP_TZSP_PORT`, default 37008), and the CHR must reach it. The Proxmox guide gains the steps:
a RouterOS user with only the sniffer read/write policy, and a firewall rule allowing TZSP only
from the CHR to the DeepLook host.

### 5.5 Plan for the test against the real Proxmox

An on-demand script, `scripts/sandbox-real-check.mjs`, run against the owner's installation, which
discards everything at the end:

1. Checks the configuration: PVE version, template exists, the account's effective permissions
   (`/access/permissions`), ISO storage.
2. Opens an environment with a harmless file (a `.txt` and a script that makes a DNS query and an
   HTTP request to a test domain).
3. Checks the console (the VNC handshake), the agent (`get-osinfo`, process list), the screenshot,
   Sysmon (if present) and the network capture (if present), with a time limit per step.
4. Closes the environment and checks the cleanup: VM deleted, ISO removed, MAC out of the sniffer.
5. Prints a step-by-step report (ok, failed with the reason, skipped because not configured) and
   exits with an error if something mandatory failed.

It uses DeepLook's own API (with an admin token), not Proxmox directly, to test the real path. No
one runs it in CI: it needs the owner's infrastructure. Implementation after this plan, to be
confirmed.
